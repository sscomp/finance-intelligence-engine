## 1. 介面定位

Hermes cron job 改寫（Phase 2C）後，每個 cron job 的 prompt 會變成：

```
1. POST http://127.0.0.1:8788/tasks 帶 {"report_type": "macro_daily", "triggered_by": "cron"}
2. 每 5 秒 GET /tasks/{task_id} 直到 status 為終態
3. 從 task 物件取 report_text 欄位，原樣送 telegram
4. footer 加 "📋 task_id: ..." 跟 "🤖 generated by: ... v..."
```

對外契約就是 `POST /tasks` 跟 `GET /tasks/{task_id}`，其餘為輔助。

---

## 2. CLI 對應（Hermes 環境友善）

Hermes 是個 hermetic 環境，每多一個長期 HTTP 服務就多一個監控負擔。Phase 2A
草案同時提供 **CLI 等效**介面，未來若 dispatcher 沒啟動，cron prompt 仍可 fallback
走 CLI。

CLI 範例（design only）：

```bash
# 建立 task
macro-report-cli task create \
  --report-type macro_daily \
  --triggered-by cron \
  --cron-job-id ed214c19c4ac

# 輸出（JSON）：
# {"task_id": "macro_daily_20260708_a3f9c2", "status": "queued", ...}

# 查狀態
macro-report-cli task status macro_daily_20260708_a3f9c2

# 列任務
macro-report-cli task list --report-type macro_daily --latest 1

# rerun
macro-report-cli task rerun macro_daily_20260708_a3f9c2 \
  --reason "data stale 5 days"

# cancel
macro-report-cli task cancel macro_daily_20260708_a3f9c2 \
  --reason "user requested"

# 取 artifact
macro-report-cli task artifact macro_daily_20260708_a3f9c2 \
  --output /tmp/macro_daily_20260708.txt
```

**Phase 2A 不實作 CLI**，但 endpoint 設計保留 CLI 對應。

## 3. Endpoints（HTTP — Phase 2C 才實作）

### 3.1 `POST /tasks` — 建立 task

**Request**：

```json
{
  "report_type": "macro_daily",
  "triggered_by": "cron",
  "cron_job_id": "ed214c19c4ac",
  "metadata_overrides": {
    "data_freshness_days": 1
  }
}
```

| 欄位 | 必填 | 說明 |
|---|---|---|
| `report_type` | Y | enum 4 選 1 |
| `triggered_by` | Y | `cron` / `manual` / `rerun` / `orchestrator` |
| `cron_job_id` | N | 若是 cron 觸發，帶 cronjob ID |
| `metadata_overrides` | N | 覆寫 manifest 預設值（例：強制 data_freshness） |

**Response 201**：

```json
{
  "task_id": "macro_daily_20260708_a3f9c2",
  "status": "queued",
  "report_type": "macro_daily",
  "created_at": "2026-07-08T08:30:00+08:00",
  "poll_url": "/tasks/macro_daily_20260708_a3f9c2",
  "events_url": "/tasks/macro_daily_20260708_a3f9c2/events"
}
```

**錯誤**：

- `400` — 未知 `report_type`
- `409` — 同 `(report_type, date, triggered_by=cron)` 已存在 active task
- `503` — dispatcher 維護中

### 3.3 `GET /tasks` — 列任務（過濾查詢）

**Query 參數**：

| 參數 | 型別 | 說明 |
|---|---|---|
| `report_type` | string | enum 過濾 |
| `date` | `YYYY-MM-DD` | Asia/Taipei 觸發日 |
| `status` | string | 過濾狀態（comma-separated：`failed,cancelled`） |
| `latest` | int | 取最新 N 筆（預設 1） |
| `since` | string | `24h` / `7d` / `2026-07-01T00:00:00+08:00` |
| `limit` | int | 上限，預設 50，max 500 |

**範例 1**：`GET /tasks?report_type=macro_daily&date=2026-07-08&latest=1`

### 3.4 `POST /tasks/{task_id}/rerun` — 重跑

**Request**：

```json
{
  "reason": "data stale 5 days",
  "force": false,
  "metadata_overrides": {
    "data_freshness_days": 1
  }
}
```

| 欄位 | 必填 | 說明 |
|---|---|---|
| `reason` | Y | 留 audit，寫入新 task 的 `task_events` |
| `force` | N | 預設 `false`，若原 task 仍在 running 則拒絕（409）；`true` 強制 cancel + rerun |
| `metadata_overrides` | N | 覆寫 manifest 預設值 |

**Response 201**：

```json
{
  "task_id": "macro_daily_20260708_d7e2f1",
  "status": "queued",
  "rerun_of": "macro_daily_20260708_a3f9c2",
  "created_at": "2026-07-08T14:25:00+08:00",
  "poll_url": "/tasks/macro_daily_20260708_d7e2f1"
}
```

**錯誤**：

- `404` — 原 task_id 不存在
- `409` — 原 task 仍在 running 且 `force=false`
- `422` — 原 task 已是 cancelled，rerun 沒意義（用 `force=true` 重置）

---

### 3.5 `POST /tasks/{task_id}/cancel` — 取消

**Request**：

```json
{
  "reason": "user changed mind, will trigger manually"
}
```

**Response 200**：

```json
{
  "task_id": "macro_daily_20260708_a3f9c2",
  "status": "cancelled",
  "cancelled_at": "2026-07-08T08:30:05+08:00",
  "previous_status": "running"
}
```

**錯誤**：

- `404` — task_id 不存在
- `409` — task 已是 terminal 狀態（completed / failed / cancelled / partial）

## 4. Auth 與 Rate Limit

Phase 2A 草案：

- **本地 loopback only**（`127.0.0.1:8788`）— 不對外暴露
- **無 auth**（loopback 即 trust boundary）
- **Rate limit**：`POST /tasks` 每分鐘 60 次（防止 cron agent 無限 retry）
- **Audit**：所有寫入 endpoint 記 `event=api_call, source_ip, ua`

Phase 2C 對外暴露時再加 bearer token（沿用 hermes-runtime-bridge 的 API key 機制）。

## 5. 與 Hermes cronjob 的分工

| 職責 | Hermes cronjob | Dispatcher（Phase 2C） |
|---|---|---|
| 何時觸發 | ✅ | ❌（被動接收） |
| 跑哪個 script | ✅（prompt 直接寫） | ❌（dispatcher 自己叫 plugin） |
| 派送 telegram | ✅（抓 stdout） | ❌（回傳 `report_text` 給 cron agent，cron agent 仍送 telegram） |
| task lifecycle 紀錄 | ❌ | ✅ |
| retry / backoff | ❌（最多自己再排一次） | ✅（worker 內建） |
| Orchestrator GPT 查狀態 | ❌（無 query API） | ✅（HTTP /tasks） |

**明確分工**：Phase 2C 之後 telegram 派送仍由 cron agent 負責（凍結行為），dispatcher
**只負責** task lifecycle + report_text 回傳。
